# Frozen acceptance — remember timestamp format

Plan baseline: `9609e28fb458c32510053458e4609a090fa9c729`, 2026-10-01. Written before implementation. These criteria are the review contract; implementation must not rewrite them to fit code. Any later change requires an explicit logged plan amendment and renewed verification.

Scope supplied in task: “this repo plus factory skills/methodology from conversation”. User feature: “remember timestamp format across navigation relaods”. Inferred product scope: one preference for all existing `useTimeFormat()` consumers within a browser origin. No authenticated profile, backend, cross-origin/network sharing, new UI, or mandatory live cross-tab synchronization. Fixed-format components keep their explicit formatting.

1. **AC1 — Preserve interaction.** Fresh browser state uses relative time. Each existing control cycles relative → local → utc → unix → relative. Titles continue to label UTC as `UTC`; formatting, timestamp values, timezone presentation, and accessible button behavior remain unchanged.
2. **AC2 — Share within a tab.** A user selection becomes the preference for all mounted and subsequently mounted `useTimeFormat()` consumers in that tab. Navigating between blocks, tokens, address, policy, and transaction pages does not reset it. Back/forward and unmount/remount retain the preference.
3. **AC3 — Persist durable choices.** With working localStorage, each selected mode survives full reload on the same origin, including a direct load of a different participating route. Initialization never overwrites an existing valid choice with the default before restoration. Other preferences/storage keys remain unchanged.
4. **AC4 — Validate saved input.** Only exact values `relative`, `local`, `utc`, and `unix` are accepted. Missing, malformed, empty, differently cased, or future unknown values fall back to relative, without exceptions or broken rendering. A subsequent valid selection can be saved.
5. **AC5 — Degrade safely.** Throwing access to localStorage, getItem, or setItem never prevents rendering or cycling. A chosen mode remains usable and shared through same-tab navigation when persistence fails; durable survival of a reload is not required when storage is unavailable.
6. **AC6 — Hydrate safely.** Server rendering requires no browser globals and does not inherit another request/browser's selection. Server markup and the initial hydration snapshot agree on the fallback; after hydration a valid saved preference is applied without a new format-related hydration warning. Brief fallback display before hydration is acceptable.
7. **AC7 — Preserve transition ordering.** Rapid sequential cycles and functional updates advance from the current preference, including updates by different hook instances. Mounting/unmounting, subscribing/unsubscribing, or Strict Mode replays cannot reset/duplicate a user change, overwrite saved state with defaults, or leave leaked active listeners.
8. **AC8 — Prove the candidate.** Focused automated tests cover AC1–AC7; real browser evidence covers actual control interaction, route navigation, reload, valid restoration, and no new format-related hydration errors. Repository required checks and explorer build pass; independent audit, Cyclops, and remote required checks refer to the final candidate. Missing infrastructure is inconclusive, never a pass. Stop at merge-ready: do not merge or deploy.

No Antithesis campaign is required or represented as run. The research skill proposes targeted adversarial tests; this four-state browser feature does not justify provisioning a campaign.
